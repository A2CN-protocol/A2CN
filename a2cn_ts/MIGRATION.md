# A2CN TypeScript Migration Report

TypeScript port of the A2CN (Agent-to-Agent Contract Negotiation) Python
reference implementation, produced from `reference-implementation/python`
at protocol version **0.2**. This document is the eligibility evaluation,
the stack mapping, and the parity evidence.

## 2. Stack mapping

| Python | TypeScript | Notes |
|---|---|---|
| Python ≥ 3.11 (via uv) | Node ≥ 20 (built with v26) | ESM, strict TypeScript |
| FastAPI + uvicorn | **Fastify 5** | Middlewares → `onRequest`/`onSend` hooks; `Depends(verify_jwt_auth)` → per-route `verifyJwtAuth(ctx, request)`; module globals + `importlib.reload` → `createServerContext()` factory |
| httpx | native `fetch` | All network-touching functions take an injectable `fetchFn` (the respx analogue) |
| PyJWT | **jose** | ES256/EdDSA JWT create/verify |
| `cryptography` | **node:crypto** | `KeyObject` keys; JWK import/export; `dsaEncoding: "ieee-p1363"` for raw ES256 JWS signatures; DER for invitation ECDSA (mirrors Python) |
| `jcs` (RFC 8785) | **canonicalize** | Byte-identical output proven by parity vectors |
| `uuid.uuid5` | **uuid** (`v5`) | Same A2CN namespace `f4a2c1e0-…` |
| `mcp` (FastMCP) | **@modelcontextprotocol/sdk** + zod | Tools also callable directly via `createMcpContext()` |
| pytest + pytest-asyncio + respx | **vitest** | httpx ASGI transport → `app.inject()`; respx → injectable fake `fetchFn` |

## 3. Test parity

- Python: `uv run --extra dev pytest -q` → **474 passed**.
- TypeScript: `npm test` → **499 passed** = **474 tests mirroring the Python
  suite 1:1** (`tests/`) **+ 25 cross-language parity-vector tests**
  (`parity/vectors.test.ts`) that have no Python counterpart because Python
  is the side that *generates* the vectors.

Assertion-level adaptations (same scenario, host-language idiom):

| Python assertion | TypeScript equivalent |
|---|---|
| `isinstance(priv.curve, SECP256R1)` | `key.asymmetricKeyDetails.namedCurve === "prime256v1"` |
| `pytest.raises(jwt.InvalidAudienceError / ExpiredSignatureError)` | jose error codes `ERR_JWT_CLAIM_VALIDATION_FAILED` / `ERR_JWT_EXPIRED` |
| `isinstance(store, SessionStore)` ABC check | structural method check (interfaces have no runtime type) |
| `SessionStore()` raises `TypeError` (abstract) | module exports no runtime `SessionStore` constructor |
| respx-mocked httpx routes | injectable `fetchFn` fakes |
| `unittest.mock.patch.dict(os.environ, …)` | `vi.stubEnv(…)` |

## 4. Cross-language parity evidence

1. **Golden vectors** (`parity/vectors.json`, generated by
   `parity/generate_vectors.py` from the Python implementation;
   consumed by `parity/vectors.test.ts`):
   - RFC 8785 canonical bytes: identical for nested objects, unicode,
     escapes, floats, and arrays.
   - `hash_object` outputs: identical.
   - Ed25519 JWS and invitation signatures: **byte-identical** (Ed25519 is
     deterministic).
   - Python-produced ES256 JWS/JWT: verified by the TypeScript verifier
     (ES256 signing is randomized by design, so equality is verification,
     not byte-compare).
   - A fixed fully-signed session replayed through the TypeScript state
     machine yields the **byte-identical transaction record** (same
     `record_id`, `offer_chain_hash`, `record_hash`).

   Regenerate with:
   ```bash
   cd reference-implementation/python
   uv run --extra dev python ../../a2cn_ts/parity/generate_vectors.py
   ```

2. **Same-language demos** — both `demos/two_process/run_demo.sh` scripts
   (Python and TypeScript) complete with `record_hashes_match: True`.

3. **Cross-language demos** (`parity/run_cross_demo.sh`) — the negotiation
   runs over real HTTP with one side per language, in both directions:
   - TypeScript buyer ↔ Python supplier → hashes match
   - Python buyer ↔ TypeScript supplier → hashes match

## 5. Pre-existing Python defects reproduced faithfully

Python is the reference; where its runnable examples fail, the TypeScript
port fails at the same step with the same error (verified side by side):

1. `examples/invitation_flow.py` — the hand-built supplier acceptance
   message has `protocol_act_signature` but no `acceptance_signature`, so
   `_handle_acceptance` rejects it with
   `Missing sender_verification_method or acceptance_signature` after
   "Round 1" prints. `examples/invitation_flow.ts` reproduces this exactly.
2. `examples/keelvar_demo.py` — the round-2 counteroffer signs a protocol
   act with `protocol_version: "0.1"`, but the server recomputes the hash
   with `"0.2"`, so processing fails with
   `Protocol act hash does not match message fields` after the session
   opens. `examples/keelvar_demo.ts` reproduces this exactly.

Neither defect is covered by the Python test suite (the examples other than
`llm_agent` are untested), and neither was "fixed" in the port, to keep
behavior parity with the reference.

## 6. How to run

```bash
cd a2cn_ts
npm install

npm test                 # 499 tests (474 mirrored + 25 parity vectors)
npm run typecheck        # tsc --noEmit

bash demos/two_process/run_demo.sh       # TS ↔ TS demo, asserts hash match
bash parity/run_cross_demo.sh            # TS ↔ Python, both directions

npx tsx examples/llm_agent.ts            # MockLLM bilateral negotiation
npx tsx examples/llm_agent.ts --use-claude   # requires @anthropic-ai/sdk + API key
npx tsx examples/saas_renewal.ts
npx tsx examples/mcp_agent_demo.ts
npx tsx src/mcp_server.ts                # MCP stdio server (Claude Desktop / Cursor)
```

The Redis/PostgreSQL session stores accept any client conforming to the
minimal `RedisLikeClient` / `PostgresLikeConnection` interfaces (e.g.
`redis` / `pg` wrappers); like the Python originals they are exercised with
fakes in tests and require no driver dependency.
